# تحليل آليات SaaS متعدد المستأجرين — جاهزية الإنتاج

> تحليل معمّق لآليات: الحساب، الدخول، التزويد، عزل المؤسسات، الاشتراكات/الباقات، الأدوار/الصلاحيات
> التاريخ: 2026-06-17 | الفرع: production-hardening

---

## ملخّص تنفيذي (الحكم النهائي)

المنصة **متينة معمارياً وقريبة جداً من جاهزية الإنتاج**، لكن توجد **3 ثغرات وظيفية يجب إصلاحها** قبل الإطلاق التجاري، و**4 نقاط متوسطة** يُفضّل معالجتها. الأساس (العزل، RBAC، الحدود) سليم ومُطبَّق فعلياً وليس مجرد تصميم.

| المجال | الحالة | الجاهزية |
|--------|--------|----------|
| إنشاء الحساب + التزويد | يعمل، لكن خطر "مستخدم يتيم" | 🟡 |
| تسجيل الدخول + الجلسات | سليم (Supabase + refresh) | 🟢 |
| عزل المؤسسات (multi-tenant) | سليم (TenantQuery + RBAC) | 🟢 |
| الأدوار والصلاحيات (RBAC) | ممتاز ومُطبَّق | 🟢 |
| الباقات والحدود (limits) | مُطبَّقة فعلياً على معظم المسارات | 🟢 |
| الاشتراكات والدفع | تعمل لكن بها تضارب Stripe/PayPal | 🟡 |
| مقاعد الأعضاء (seats) | **ثغرة: تجاوز عبر مسار واحد** | 🔴 |

## 1) إنشاء الحساب (Signup)

**المسار:** `POST /api/v1/auth/signup` (`app/routes/auth.py:103`)

**التدفّق الفعلي:**
1. إنشاء مستخدم في Supabase Auth عبر `sign_up` (anon key).
2. إنشاء `tenant` تلقائياً باسم المؤسسة (أو `"{name}'s Workspace"`) + slug فريد (`base-slug + token_hex(3)`).
3. إنشاء عضوية `owner` نشطة.
4. إنشاء اشتراك `starter` مجاني (period 30 يوم، trial 14 يوم).
5. تزويد المستأجر: 5 أدوار افتراضية + صلاحياتها + إعدادات + feature flags (`provision_tenant_manual`).
6. إنشاء `profile`.
7. توليد رابط تحقق بريد + إرسال إيميلات في الخلفية.

**نقاط القوة:**
- التزويد كامل وذرّي على مستوى DB (الخطوات 2–6 داخل معاملة واحدة مع `rollback`).
- الـ slug فريد، ومعالجة البريد المكرر (409).

**🔴 المشكلة الحرجة — "مستخدم يتيم" (orphan user):**
الخطوة 1 (إنشاء مستخدم Supabase) تقع **خارج** معاملة قاعدة البيانات. إذا فشل التزويد (خطوات 2–6)، الكود ينفّذ `db.rollback()` لكن **لا يحذف مستخدم Supabase الذي أُنشئ**. النتيجة:
- يبقى المستخدم في `auth.users` بلا tenant/profile.
- محاولة إعادة التسجيل بنفس البريد → خطأ 409 "مسجل مسبقاً" → **المستخدم عالق ولا يستطيع الدخول ولا التسجيل**.

**الإصلاح المقترح:** في `except`، استدعاء `supabase.auth.admin.delete_user(user_id)` للتراجع عن إنشاء المستخدم، أو نقل إنشاء المستخدم ليكون آخر خطوة بعد نجاح التزويد.

**🟡 ملاحظة:** التسجيل يفترض وجود خطة `starter` و دوال DB. إن لم تُزرع الباقات (`seed_plans.py`)، الخطوة 4 تفشل ويُلغى كل التسجيل.

## 2) تسجيل الدخول (Login)

**المسار:** `POST /api/v1/auth/login` (`app/routes/auth.py:234`)

**التدفّق:**
1. `sign_in_with_password` عبر Supabase (anon key) → access + refresh tokens.
2. تحديث `last_login_at`.
3. جلب مستأجري المستخدم النشطين (`get_user_tenants_with_roles`).
4. إن كان لديه **أكثر من مستأجر** ولم يُحدّد واحداً → `requires_tenant_selection=true` مع قائمة المستأجرين.
5. وإلا → إرجاع التوكنات مباشرة.

**نقاط القوة:**
- منطق اختيار المستأجر صحيح للمستخدم متعدد المؤسسات.
- معالجة الأخطاء العامة (401 موحّد لا يكشف إن كان البريد موجوداً).
- تحديث/تجديد التوكن في الواجهة تلقائي (interceptor في `client.ts`).

**🟢 الحالة:** سليم وجاهز.

**ملاحظة بسيطة:** `except Exception: pass` في تحديث `last_login_at` و جلب المستأجرين يبتلع كل الأخطاء بصمت. مقبول للمرونة لكن يُفضّل تسجيلها بـ logging.

## 3) عزل المؤسسات (Multi-Tenant Isolation)

**الآلية مزدوجة الطبقات:**

**أ) حلّ المستأجر** (`TenantResolutionMiddleware`): header `X-Tenant-ID/Slug` → subdomain → custom domain. يفرض حالة المستأجر (active/trial فقط).

**ب) فرض العزل على مستوى التطبيق:**
- كل عملية محمية تستدعي `require_permission(db, tenant_id, user.id, key)` التي تستعلم `user_has_permission(tenant, user, key)`.
- هذه الدالة تتحقق من **عضوية المستخدم في ذلك المستأجر تحديداً** → **مستخدم من مستأجر آخر يفشل تلقائياً (403)** حتى لو زوّر الـ header. هذا هو الضمان الأساسي للعزل.
- `TenantQuery` يفرض `WHERE tenant_id = :tid` في كل استعلام.

**ج) RLS (Row-Level Security):** موجود في الـ schema (199 policy عبر الملفات)، **لكنه غير فعّال عملياً** لأن التطبيق يتصل عبر `DATABASE_URL` بدور يتجاوز RLS، وعبر service_role. 

**🟢 الحالة:** العزل سليم — لكنه **يعتمد كلياً على طبقة التطبيق** (RBAC + TenantQuery)، وليس على RLS. هذا مقبول للإنتاج **بشرط** الانضباط: أي endpoint جديد يجب أن يمرّ بـ `require_permission` + `TenantQuery`. الـ public endpoints (view/rsvp) تستعلم بالـ token فقط وتُرجع حقولاً آمنة — مُراجَعة وآمنة.

**🟡 توصية:** بما أن RLS غير مُستخدَم، إمّا تفعيله كطبقة دفاع ثانية (defense-in-depth) أو حذف الـ policies المضلّلة لتجنّب وهم الأمان.

## 4) الأدوار والصلاحيات (RBAC)

**النموذج:** `roles` (لكل مستأجر) → `role_permissions` → `permissions` (عامة). و `memberships.role` (owner/admin/member/...) + `membership_roles` (أدوار RBAC مخصّصة).

**دالة `user_has_permission`** (مفتاح النظام):
```
owner/admin  → كل الصلاحيات تلقائياً (bypass)
غير ذلك      → فحص membership_roles ⋈ role_permissions
```

**التزويد ينشئ 5 أدوار:** Admin (كل الصلاحيات)، Member (إدارة أحداث/دعوات)، Designer (قوالب)، Check-in Staff (مسح)، Viewer (قراءة). كل دور له مفاتيح API ومفاتيح `ui.*` (للتحكم في واجهة المستخدم).

**نقاط القوة:**
- فصل نظيف بين صلاحيات API و صلاحيات الواجهة (`ui.*`) مع نظام aliases يربطهما.
- owner/admin bypass منطقي وآمن (مقيّد بالعضوية النشطة في نفس المستأجر).
- الصلاحيات الافتراضية مدروسة ومنطقية لكل دور.

**🟢 الحالة:** ممتاز وجاهز للإنتاج. هذا أقوى جزء في النظام.

## 5) الباقات والحدود (Plans & Limits)

**5 باقات:** Starter (مجاني) → Basic → Pro → Business → Enterprise، مع 14 نوع حد لكل باقة (مقاعد، أحداث/شهر، دعوات، فرق، تخزين، AI...). `-1` = غير محدود.

**الفرض الفعلي (تم التحقق منه في الكود):**
| الحد | يُفرض في | الحالة |
|------|----------|--------|
| `events_per_month` | `events.py:106` (`enforce_monthly_limit`) | ✅ |
| `invitations_per_month` | `events.py:109` (عند إنشاء الحدث) | ✅ |
| `guests_max` | `guests.py:50,155` | ✅ |
| حصص الدعوات/حدث (vip/normal) | `quota_service` في 4 مسارات إنشاء | ✅ |
| `storage_mb` | `feature_service.require_storage_for_upload` | ✅ |
| `seats_max` | `invites.py:15` فقط | ⚠️ ثغرة (انظر أدناه) |

**حلّ الحد** يتدرّج: custom_plan → subscription نشط → plan في جدول tenants (fallback). منطقي ويغطّي الخطط المخصّصة.

**الميزات (feature flags):** `check_feature_flag` يدمج override صريح + تدرّج حسب الباقة. تُفرض عبر `require_feature`.

**🟢 الحالة:** الحدود مُطبَّقة فعلياً (ليست تصميماً فقط) — وهذا ممتاز ونادر. باستثناء ثغرة المقاعد التالية.

## 6) الاشتراكات والدفع (Billing)

**المزودان:** PayPal و Stripe، كلاهما عبر checkout + webhooks موقّعة.

**نقاط القوة:**
- التحقق من توقيع webhook في كليهما (`verify_webhook_signature` / `construct_event`). ✅
- `subscription_events` يسجّل كل أحداث webhook (سجل تدقيق مالي).
- Stripe يعالج: `checkout.completed`, `invoice.paid`, `payment_failed` (→ past_due), `subscription.deleted` (→ downgrade تلقائي لـ starter). شامل.
- إلغاء الاشتراك يُنفّذ لدى المزوّد فعلياً (cancel_at_period_end).

**🟡 المشكلة 1 — تضارب تحديث `tenants.plan`:**
- مسار **PayPal** (`execute_paypal_subscription:309`) يحدّث عمود `tenants.plan`.
- مسار **Stripe** (`stripe_webhook:528`) ينشئ صف subscription لكن **لا يحدّث `tenants.plan`**.
- بما أن `feature_service` يعتمد أولاً على جدول `subscriptions` (وليس `tenants.plan`)، الأثر محدود — لكن أي كود يقرأ `tenants.plan` مباشرة (مثل middleware حلّ المستأجر، و fallback الحدود) سيرى الباقة القديمة. **يجب توحيد السلوك.**

**🟡 المشكلة 2 — لا فرض على "ترقية الباقة" بأثر رجعي:**
عند التنزيل (downgrade) لا يوجد فحص إن كان الاستخدام الحالي يتجاوز حدود الباقة الأدنى (مثلاً 10 أحداث على باقة تسمح بـ 3). يُنصح بسياسة واضحة (منع/تجميد الزائد).

**🟡 المشكلة 3 — `current_period_end` ثابت 30 يوماً:**
يُحسب بـ `now() + INTERVAL '30 days'` بدل قراءة التاريخ الفعلي من المزوّد (Stripe يوفّره في `invoice.paid`). قد ينحرف عن دورة الفوترة الحقيقية.

## 7) 🔴 الثغرة الحرجة: تجاوز حد المقاعد (Seats)

هناك مساران لإضافة عضو:
1. **`POST /invites`** (`invites.py:15`) → يستدعي `check_seats_limit` ✅
2. **`POST /tenants/current/members`** (`tenants.py:297`, `create_member`) → **لا يستدعي `check_seats_limit`** ❌

`create_member` ينشئ مستخدماً ويضيفه مباشرة دون فحص حد `seats_max`. **أي مستأجر على باقة Starter (حد مقعدين) يستطيع إضافة أعضاء بلا حدود عبر هذا المسار** — تجاوز مباشر لقيود الباقة (خسارة إيراد + سوء استخدام موارد).

**الإصلاح:** إضافة `await check_seats_limit(db, tenant_id)` قبل الإنشاء في `create_member`، تماماً كما في `invites.py`.

## قائمة الإصلاحات المطلوبة قبل الإطلاق

### 🔴 حرجة (يجب)
1. **ثغرة المقاعد**: إضافة `check_seats_limit` في `tenants.py:create_member`.
2. **المستخدم اليتيم في signup**: حذف مستخدم Supabase عند فشل التزويد.
3. **توحيد `tenants.plan`**: مسار Stripe يجب أن يحدّث العمود مثل PayPal (أو إزالة الاعتماد على العمود كلياً).

### 🟡 متوسطة (يُنصح بشدة)
4. **سياسة downgrade**: ✅ **مُنفَّذ** — `check_downgrade_allowed` في `feature_service.py` يمنع التنزيل (409) إن تجاوز الاستخدام القائم حدود الباقة الهدف للموارد الدائمة (الأعضاء/الفرق/الضيوف/التخزين)، ومربوط عند نقطة تغيير الباقة `create_checkout_session`. الحدود الشهرية (الأحداث/الدعوات) تُفرض عند الاستخدام لأنها تتصفّر دورياً.
5. **`current_period_end`**: قراءته من بيانات المزوّد بدل +30 يوم ثابت.
6. **RLS**: ✅ **حُسم** — قرار موثّق (`docs/adr/0001-rls-not-active-isolation.md`): العزل يبقى على طبقة التطبيق (RBAC + TenantQuery) كمصدر وحيد للحقيقة، وأُضيف تعليق تفسيري في رأس قسم RLS بـ `schema.sql` لإزالة وهم الأمان. الـ policies تُترك كتوثيق وأساس جاهز لـ defense-in-depth مستقبلاً.
7. **ابتلاع الأخطاء الصامت** في login/me: استبدال `except: pass` بـ logging.

### 🟢 جاهز فعلاً
- تسجيل الدخول والجلسات وتجديد التوكن.
- عزل المؤسسات عبر RBAC + TenantQuery.
- نظام الأدوار والصلاحيات (RBAC) الكامل.
- فرض حدود الأحداث/الدعوات/الضيوف/التخزين/الحصص.
- التحقق من توقيع webhooks وتسجيل الأحداث المالية.

## الخلاصة

النظام **ليس نموذجاً أوّلياً — هو منصة SaaS مكتملة** بعزل حقيقي وRBAC قوي وفرض حدود فعلي. الفجوات المتبقية محدّدة وقابلة للإصلاح بسرعة (الأهم: 3 إصلاحات حرجة، أبرزها ثغرة المقاعد في سطر واحد فعلياً). بعد معالجة القائمة الحرجة (🔴)، المنصة **جاهزة للإطلاق كـ SaaS متعدد المستأجرين**.

> ملاحظة منهجية: هذا التحليل قائم على قراءة الكود الفعلي. لم أتمكّن من تشغيل اختبار حيّ للتدفقات (لا توجد خدمات تعمل في هذه البيئة)، لذا يُنصح باختبار تكامل للمسارات الثلاثة الحرجة بعد إصلاحها.
